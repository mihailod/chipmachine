1. The Mod Archive
URL: [https://modarchive.org](https://modarchive.org)
What it is: The single largest, active repository for tracker modules (.mod, .xm, .it, .s3m). While Modland is a massive raw FTP dump, Mod Archive is highly curated, reviewed, and rated by the community. Essential for tracker history.  
The Mod Archive (Do Not Scrape)
The site explicitly bans generic scrapers. However, they maintain their own official BitTorrent tracker specifically so users can download the entire site in bulk blocks.
Navigate directly to http://tracker.modarchive.org/
Download the core snapshot torrents (e.g., modarchive_2007_official_snapshot_120000_modules) which forms the massive base archive.
Download the chronological addendum torrents (e.g., modarchive_2012_additions, etc.) to bring your local collection up to date.

2. ExoticA / UnExoticA
URL: [https://www.exotica.org.uk](https://www.exotica.org.uk)
What it is: You have janeway.exotica.org.uk listed under demo databases, but you are missing the main site's crown jewel: UnExoticA. It tracks custom, exotic Amiga game music formats that don't fit into standard trackers (e.g., TFMX, Custom, HippoPlayer formats, Sonic Arranger).
The site is heavily indexed and explicitly hosts single-file download collections for its entire music subsystem so you don't have to scrape thousands of individual game folders.
Navigate to https://www.exotica.org.uk/wiki/UnExoticA
Scroll to the downloads section. They provide a master collection pack (usually a massive .lha or .zip file containing all the exotic custom formats like TFMX and Sonic Arranger grouped by author/game).

3. VGMRips
URL: [https://vgmrips.net](https://vgmrips.net)
What it is: The premier home for .vgm (Video Game Music) file logs, focusing heavily on arcade boards (Capcom CPS1/2/3, Sega system 16, Neo Geo) and sound chips like the YM2612, YM2151, and AY-3-8910.
VGMRips (Use the Server Admin's Zip)
The Reality: VGMRips is a database front-end. Scraping individual pages for .vgm packs will get your IP blocked. The former server host maintains an official, all-in-one compressed file.
Go directly to the VGMRips forum thread: https://vgmrips.net/forum/viewtopic.php?t=496
The thread is titled "VGMRips full download packs".
Download the single aggregated zip file (VGMRips_all_of_them_[DATE].zip). It sits around 4 to 5 GB and contains every single pack logged on the site up to its compilation date.

4. Project 2612 & SMS Power!
URLs: [https://project2612.org](https://project2612.org) | [https://www.smspower.org](https://www.smspower.org)
What they are: Definitive, dedicated system vaults. Project 2612 is the definitive source for Sega Genesis/Mega Drive .vgm rips. SMS Power handles Sega Master System, Game Gear, and SG-1000 audio logging.
These sites are simple, predictable directory trees. They do not block standard command-line tools if you throttle your requests.
Project 2612 (Sega Genesis)
Use wget to cleanly mirror the entire structured .vgm archive directory. Use a mirror flag, reject HTML files, and add a mandatory delay to avoid triggering server alerts:
Bash
wget --mirror --no-parent --no-host-directories \
     --reject "index.html*" --wait=1 --random-wait \
     https://project2612.org/vgm/
SMS Power! (Sega Master System / Game Gear)
SMS Power hosts pre-packaged zip files of their entire music section.
Bash
wget --mirror --no-parent --accept "*.zip" \
     --wait=1 --random-wait \
     https://www.smspower.org/Music/

What it is: Focuses heavily on Japanese PC-88, PC-98, Sharp X68000, and FM-towns game music logs. Essential if you want to dig into the PMD/PMD88 trackers and Yamaha FM-synthesis mastery.

Engineering Commentary:
   1. The "Blocking" Logic in AyflyPlugin:
       * Your hunch is correct. Many legacy chiptune archives (like the old Project AY) bundled Quartet files under the .ay extension. 
       * libayfly is a specialized emulator for AY-chip register dumps (like Spectrum or Amstrad CPC music). Quartet, however, is a software-mixing sample tracker for the Atari ST. 
       * If Ayfly tried to "play" a Quartet file, it would be interpreting 68000 machine code as AY register writes, leading to catastrophic noise. The block in AyflyPlugin.cpp is a safety guard against this common mislabeling in music databases.
   2. Implementation Feasibility: Moderate (leaning towards Easy)
       * The "Gold Standard" Library: You should look at zingzong by Benjamin Gerard (Ben/OVR). It is a portable, MIT-licensed C library specifically designed to play Microdeal Quartet files (.4v, .set, .4q).
       * Multi-file Challenge: The primary engineering hurdle is that Quartet is often split into two files: the song data (.4v) and the voice set (.set). 
       * ChipMachine Advantage: ChipMachine already has an infrastructure for "secondary files" (used for Richard Joseph Amiga songs and .ins files). Implementing a QuartetPlugin would simply mean using the
         getSecondaryFiles() hook to tell the player to look for the matching .set file in the same directory.
   3. The .4q Variant:
       * In the Atari ST scene, .4q is a "packed" version that bundles both the .4v and .set into one file. Supporting .4q would be even easier as it is self-contained.
  Technical Verdict:
  Quartet ST is a prime candidate for a native plugin. It represents the "missing link" between early beeper music and the ProTracker/MOD era on the Atari. By integrating the zingzong library, you could resolve the AyflyPlugin conflict properly by having a dedicated handler that actually plays the music instead of just blocking the path.
  Recommendation: Upgrade status to "Highly Feasible." The existence of a clean, portable C replayer (zingzong) removes 90% of the implementation risk.

174	.symmod	Symphonie (Amiga)	Moderate	Amiga tracker from ~1993; UADE has partial support for similar formats; some source floating around
  The research for Symphonie (.symmod) reveals a format that is much more sophisticated—and more difficult—than the "Moderate" rating suggests.
  1. Technical Complexity: Hard (not Moderate)
   * The "Pseudo-DAW" Problem: Symphonie was essentially a precursor to modern DAWs on the Amiga. It didn't just play samples; it had a software-mixing engine with up to 256 channels and real-time software DSP (reverb, echo, resonant filters).
   * Assembly Dependency: The authoritative source code and replayers are written in 68k Assembly (optimized for 68030/040/060). There is no "clean" portable C replayer that accurately reproduces the software filters and effects.
  2. Re-evaluating Implementation Options:
   * Option A: Native Port (Very Hard): You would have to manually translate thousands of lines of 68k Assembly into C or a modern synthesis engine. Given the complexity of its software mixer, this is a massive undertaking.
   * Option B: UADE (The Path of Least Resistance): You mentioned UADE has partial support. Actually, UADE's support for Symphonie is quite robust because it runs the original Amiga player binary in a 68k emulator. 
       * Strategic Win: Since ChipMachine already integrates UADEPlugin, the most efficient way to support .symmod is to verify and enable it within your UADE infrastructure rather than writing a new plugin.
  3. Why it matters:
   * History: Symphonie was the "high-end" choice for Amiga musicians (like Muffler) who wanted to escape the 4-channel limitations of Protracker. The music is often lush, atmospheric, and technically impressive.
   * The Catch: Because it was so CPU-intensive, many .symmod files won't even play correctly on a base Amiga 500; they require the power of the replayer's software mixer.
  4. Summary of Findings:
   * Format: Symphonie Pro Module (.symmod).
   * Sound Engine: 256-channel Software Mixer + Real-time DSP effects.
   * Source Availability: Open source (68k Assembly) on Aminet and GitHub (MastaTabs).
   * Effort: Hard for a native port; Easy if routed through your existing UADEPlugin.
  Recommendation: 
  Do not attempt a native C implementation of Symphonie. Instead, focus on routing .symmod files to your UADE plugin. You will likely find that UADE already handles the heavy lifting of emulating the software mixer, giving you the "big sound" of Symphonie with minimal code changes.

   * Correction: TFM Music Maker (.tfe) does not use OPL2 (2-operator FM). It is designed for TurboSound FM, which uses dual YM2203 (OPN) chips.

   * Impact on Feasibility: AdPlugin (the project's OPL infrastructure) is useless for this format. You cannot "reuse" OPL2/OPL3 code to play OPN music; they are entirely different architectures (2-op vs 4-op, different registers, different feedback algorithms).
  2. Feasibility Re-assessment: Hard (not Moderate)

       1. Integrate an OPN2/OPN emulator: You already have libopna in the project (from the 98fmplayer folder), which can emulate a YM2203. However, you'd need to instantiate two of them to support the 6 FM channels of a TFM module.
       2. Port the Tracker Logic: Since there is no standalone C/C++ library for .tfe (like libopenmpt), you would have to manually port Shiru's original playback logic (which is likely in Delphi or Assembly) into your C++ MusicPlayer plugin.
       3. Alternative (The "Easy" Way): Most .tfe files are often converted to .vgm or .tfd (register dumps). If the goal is just to "play the music," it is 100x easier to support .vgm (which you likely already do or can easily add via libvgm) than to natively parse and play a .tfe module.
  3. Summary of Findings:
   * Format: Native TFM Music Maker Module.
   * Sound Chip: Dual Yamaha YM2203 (OPN).
   * Existing Infrastructure: The project's libopna is a good starting point, but AdPlugin is irrelevant.
   * Source Code: Available (Shiru’s stuff is usually on GitHub or his website), but it is a "from scratch" plugin effort.
  Recommendation: Do not pursue native .tfe support under the assumption that it's "just another OPL format." It is a Sega-Genesis-class FM format. If you want these songs in ChipMachine, look for the VGM versions of them instead.

IMPOSSIBLE 535	.psy	Psycle tracker	Hard	Open-source tracker (psycle.sf.net) but the file format is complex and there's no standalone decode library
Psycle (.psy) - Modular Tracker
   * Status: Unsupported.
   * Research: Psycle is an open-source modular tracker, but the .psy format is essentially a dump of the internal state. 
   * Feasibility: Hard. There is no standalone "playback-only" library; supporting it would require porting a large portion of the Psycle engine.
✦ The assessment that Psycle (.psy) support is "Hard" and currently unfeasible is 100% accurate. 
here is the technical breakdown of why this is a "no-go" for a lightweight player like ChipMachine:
   1. Modular vs. Linear Architecture: Unlike standard trackers (MOD, XM, IT) where playback logic is fixed, Psycle is a modular environment. This means the sound is determined by a complex graph of internal "machines" (oscillators, samplers, filters) and VSTs. Supporting .psy isn't just about parsing a file; it's about embedding a whole virtual synthesis engine.
   2. The "SunVox" Comparison: You might ask, "Why does ChipMachine support SunVox then?" The difference is that the SunVox developer provides a standalone, portable C library (sunvox.dylib) specifically for third-party developers. Psycle has no such library; the playback logic is tightly coupled with the host application's GUI and OS-specific VST handling.
   3. State Dump vs. Data Format: As your research noted, .psy files are often closer to a memory snapshot of the application state than a structured music format. Recreating the audio path outside of the original Psycle environment would require a massive reverse-engineering effort or porting thousands of lines of GPL code, which would bloat the app significantly.
   4. Lack of libopenmpt Support: Since libopenmpt (the industry standard for tracker playback) doesn't support it, there is no "easy win" for integration.
  Verdict: Keep it in the "Unsupported" category. Unless someone creates a standalone "Psycle-lite" rendering library, the ROI for manual implementation is nearly zero given the rarity of the format compared to the effort required.

IMPOSSIBLE 152	.xrns	Renoise (modern)	Hard	Proprietary zipped XML format; no open-source decoder; Renoise SDK is closed
   * Structure: While .xrns is just a ZIP of XML and samples (easy to parse), it is not a self-contained module like an .it or .xm file.

IMPOSSIBLE 120	.rns	Renoise old format	Hard	Explicitly blocked in OpenMPTPlugin (if (ext == "rns") return false); likely undecodable without Renoise itself
✦ The .rns format (Renoise versions 1.0–1.5) is indeed a "Hard" target. Here is the feasibility report:
  1. The Nature of the Format
   * Proprietary Binary: Unlike the modern .xrns format (which is a standard ZIP archive containing XML and audio samples), the old .rns format is a closed, proprietary binary structure.
   * Header: It can be identified by the ASCII string RENOISE SONG V at the start of the file.
   * Complexity: As a DAW-style format (rather than a simple module), it includes complex DSP chains, internal
     synthesizer settings, and automation that are not easily mapped to standard tracker engines like OpenMPT.
  2. Why it is Blocked
   * No Native Loader: libopenmpt (the engine behind ChipMachine's OpenMPTPlugin) does not have a loader for .rns. It was never reverse-engineered by the OpenMPT team.
   * Avoiding False Positives: The explicit block in OpenMPTPlugin.cpp (if (ext == "rns") return false;) exists because some .rns files might be misidentified by other generic loaders, leading to crashes or garbage audio output when the engine tries to force-parse them as something else (like an old NoiseTrekker file).
  3. Feasibility of Support
   * Open Source Decoders: There are no known standalone open-source decoders for the legacy binary .rns format.
   * Partial Path (NoiseTrekker): Renoise was the successor to NoiseTrekker (.ntk). While ProTrekkr is an open-source project that can play .ntk files, it does not support the expanded binary format used in Renoise 1.0+.
   * The Only Real Fix: The standard community advice is to use a slightly older version of Renoise (around 1.8/1.9) to open the .rns files and resave them as .xrns. However, even .xrns is poorly supported by tracker libraries because it relies on Renoise's internal DSP engine to sound "correct."
  Conclusion
  Support for .rns is unlikely without a massive reverse-engineering effort or the release of the original Renoise 1.0 source code. The "Explicitly blocked" status in your plugin is correct; it prevents the engine from attempting to play a format it fundamentally does not understand.
